代码库瘦身小故事

我只做了检查，没有删除任何东西。你来决定哪些东西真的该留下。

第一步

先找“没人用的玩具”

代码库像一个工具箱。真正的 wb 主流程都有调用者，测试也能通过：101 个测试通过，ruff 检查通过。

所以我没有把核心的校正、改写、失败回退、资产查找删掉。它们虽然看起来复杂，但在保护录音不丢失。

候选 A - 高把握

删掉四个已经过时的包装纸

这些文件一共 161 行、约 5.2 KB：scripts/run.sh、scripts/test.sh、scripts/test_play.sh、带日期的 audio_trim_silence_260303_whisper.sh。

run.sh 还在调用不存在的 uv run main 和已经退休的参数；另外三个写死了旧电脑的绝对路径。仓库的代码、文档、CI 都没有调用它们。

替代：什么也不加。日常使用直接用 wb；需要播放器可保留通用的 play.sh。

候选 B - 请你决定

四个独立小工具要不要搬走

audio_trim_silence.py、detect_audio_segments_by_db.py、sync_subtitles.py、video_trim_ffmpeg.py 都没有被主程序、文档或 CI 调用，也不会被打进安装包。

但它们是通用工具，不一定是垃圾；历史上的重构计划还明确写过“保留四个媒体工具”。

如果仓库只负责 wb：可以删除，或移到单独的工具仓库。如果你还手工用它们：留下，并补一小段使用说明。

候选 C - 小幅瘦身

说明书可以少写一点过程话

两个 README 里的“双语文件要同步”是给维护者看的，不是用户运行 wb 必需的；可以删掉，保留顶部语言链接和架构链接。

架构文档也能把“为什么这样设计”的长解释压成直接规则，但要保留命令、默认值、失败回退和“不丢稿”的安全约束。

这会让说明书更短，但不会改变程序行为。

我建议先选 A

它们确定过时、没有调用者，删掉后不用替代品，风险最低。

B 要看你的习惯

你若手工用媒体工具，就别删；若从没用过，移走能让主仓库更清楚。

C 可以最后做

它主要减少阅读负担，收益小于 A 和 B，不急。

一句话：先扔掉坏掉的旧包装纸；工具箱里的真正工具，先问主人再扔。
